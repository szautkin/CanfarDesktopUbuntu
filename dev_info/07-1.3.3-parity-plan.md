## 4. The plan

Ordered so that each phase leaves the tree shippable, and so the "100% MCP UI coverage" goal lands first.

### Phase 0 — Land the WIP (S) — **DONE**
Landed in four commits: the in-flight sweep, the 1.3.3 QA fixes, a tree-wide `cargo fmt`, and a
hygiene pass that made `cargo clippy -- -D warnings` pass for the first time on this branch.

Clearing the lint noise surfaced two real defects it had been hiding:
- **The stdio bridge test was talking to the developer's running app.** It isolated itself with
  `$XDG_RUNTIME_DIR`, but `socket_path()` deliberately ranks the uid-derived `/run/user/<uid>` higher
  (so the bridge still finds the app when a launcher strips the environment). On any systemd host the
  override did nothing. Added `VERBINAL_MCP_SOCKET`, an explicit full-path override that beats every
  other rule, and pointed the test at it.
- **`filter_to_adql` was compiled twice** — `search_page.rs` pulled it in via `#[path]` while
  `helpers/mod.rs` already declared it, so its 8 tests ran in duplicate. (This is why the unit count
  reads 849 → 841 across those commits; no coverage was lost.)

### Phase 1 — Wire-contract parity (M) — **DONE**
All 14 tools renamed to the reference's names, `clear_user_site` implemented, and the 3 macOS aliases
added — **113 tools advertised**. 108 payload keys plus 8 `required` entries converted to camelCase.

The contract is now enforced rather than asserted: `data/canfardesktop_1.3.3_tools.txt` holds the
reference's exact 137-name manifest, and a test diffs ours against it three ways — nothing extra,
nothing missing outside a documented `NOT_YET_PORTED` backlog, and no backlog entry that is secretly
already implemented. **That backlog may only shrink**; it currently holds exactly the 24 tools Phases
2, 3 and 5 will add, so those phases tighten the test automatically as they land.

Two things worth knowing for later work:
- Renaming the tools also renamed the ops sent over the viewer bridge (the notebook and FITS hosts map
  a tool name straight through as its op). `run_all_cells`, `clear_cell_outputs` and
  `list_fits_bookmarks` would have silently failed; the host arms were aligned so tool names and bridge
  ops remain one vocabulary. **Any future tool rename must check the bridge hosts.**
- `str_arg` existed in 11 copies, with six sibling accessors scattered similarly, all reading
  `args.get(key)` directly. They are now one implementation in `mcp::tools` routing through a single
  style-tolerant `arg()`, so a caller may send either `publisherId` or `publisher_id` — matching the
  reference's case-insensitive deserialization, and keeping every pre-rename caller working.

### Phase 2 — Search MCP full UI coverage (XL) — **DONE**
All 15 tools shipped; advertised tools 113 → 128. Thirteen forward over the view-state bridge to the
live page (new `"search"` target) so an agent drives the same widgets a user does; the handler lives in
`ui::search_page::mcp`, a child module of the page (hence `search_page.rs` → `search_page/mod.rs`,
mirroring the reference's `SearchPage.Mcp.cs` split). `remove_recent_search` /
`clear_recent_searches` are Destructive proposals, and the former pins a stable
`(searchedAt, summary)` key at propose time — with a test proving that a list which shifts between
propose and apply still deletes the right entry.

The four blocking defects were fixed first (S2–S5). Two turned out to be worse than the audit said:

- **Reset never cleared the facets**, so constraints that looked cleared silently narrowed the next
  search. `reset_search_form` depended on it.
- **Pixel-scale parity carries a behaviour change**: a bare value now means `= v`, not `<= v`. Verified
  against the reference (`AddConvertedRangeClause`, `RangeOperand.Equals`) — our `<= max` was the
  divergence. Both behaviours are now pinned by tests.

Three supporting fixes fell out, each closing a real bug:
- `DataTrainManager::set_all_selections` — restoring by replaying toggles would clear downstream
  columns and wipe the very selections being restored.
- `SearchStoreService::save_all_recent` — the sidebar's delete button cleared and re-saved entry by
  entry, which reversed the order and merged entries sharing ADQL.
- `SearchFormState` gained a container-level `#[serde(default)]`: it is persisted inside every recent
  search, so without it adding one field made every saved search fail to parse and vanish silently.

Also worth carrying forward: the first version of these tests would have **deleted the developer's own
recent searches**, because `SearchStoreService::new()` points at the real user data dir. It now has a
`with_data_dir` constructor and every test uses a temp store.

### Phase 3 — FITS + Cube MCP full UI coverage (L) — **DONE**
Seven new tools (`switch_fits_tab`, `blink_fits_tabs`, `set_cube_transfer`, `show_cube_spectrum`,
`get_cube_channel_profile`, `switch_cube_tab`, `list_recent_cubes`) plus the 1.3.3 extensions to
`set_fits_view` and `get_fits_view`. Advertised tools 128 → 135.

The audit this phase was "blocked on" proved unnecessary — reading the reference's `27a4889` diff for
those files directly was faster and more targeted. The blink and sync machinery already existed from
the earlier sweep; this exposed it.

**Four real bugs surfaced, three of them invisible:**

1. **Every renamed argument was being ignored.** Phase 1b moved schemas to camelCase but only touched
   `src/mcp/tools`; the three viewer hosts still read `min_cut`, `north_up`, `center_x` and friends.
   `set_fits_view {"minCut": 0.1}` returned success and did nothing. All 28 call sites now route
   through the style-tolerant `arg()`.
2. **The guard for that had a hole.** rustfmt wraps long chains as `args\n    .get(`, which a substring
   check cannot see — 20 more sites were still broken while the guard reported clean. It now ignores
   whitespace.
3. **`probe_fits_pixel` reported no WCS on images that have one** — the payload set `"hasWcs": false`
   and then wrote `out["has_wcs"] = true` beside it, two different keys.
4. **`list_open_tabs` always returned empty arrays.** Its three setters had zero callers, so the
   snapshot was never written. Nothing noticed until this phase added tools that address a tab by index.

**Two 1.3.3 QA fixes ported:** blanked FITS pixels omit `value` (NaN is not representable in JSON, so
serializing one failed the whole call), and probing a strided cube used the resident array's bounds —
so on any downsampled cube most valid native spaxels reported "outside the cube", and those that did
answer read the wrong voxel. Native↔resident mapping is now two tested functions in `volume_data`,
shared by all three call sites that needed it.

**Source-level guards** now fail the build if a viewer host reads arguments with `args.get(` or emits a
snake_case JSON key. Unusual, but these hosts need a live GTK tree so they have no unit coverage, and
every bug above was silent by construction.

### Phase 4 — QA + reliability (S) — **DONE**
Q1–Q4 landed earlier (see §3d). The two remaining 1.3.2 items are now in:

- **Kernel deaths explain themselves.** `stderr` was discarded on the reasoning that the harness reports
  cell errors as JSON on stdout — true, but anything that kills Python BEFORE the harness runs is only
  ever explained on stderr, so the user got "exited unexpectedly" and nothing to act on. It is now
  captured and drained into the error, truncated to its tail where the cause lives.
- **Landing tiles reflow.** A fixed 3-column `Grid` clipped tiles on a narrow window and left later rows
  unreachable on a short one; now a `FlowBox` (3 → 1 per line) with horizontal scrolling refused outright.

**The reference's kernel restart race does not exist in this port**, and that was verified rather than
assumed: its bug was an exit-event handler resolving the harness file via a shared field. We have no such
handler, `&mut self` serialises starts on one service, and each launch writes a uniquely named harness so
per-tab kernels cannot collide. That uniqueness is now pinned by a test, since the whole argument rests
on it.

### Phase 5 — High-severity carry-overs (M) — **DONE**
**The CAOM2 cache was dead.** `CAOM2Service` carries a 100-entry LRU but was constructed fresh at every
call site, so every lookup missed and each observation-detail open re-issued the full 30–50s
`caom2ops/meta` request. It now lives in `AppServices`, shared by both callers.

**`download_observation` / `download_observations_bulk`** complete the tool surface at 137/137. Both are
non-destructive (they ADD to the library, so autonomy may apply them). An absent `artifactIndex` stays
absent rather than defaulting to 0 — 0 addresses a real artifact, so a default would silently pick one.
The bulk tool validates every item before queuing and names the failing index; on an apply failure it
reports how many actually landed.

Both sit on a new `services::observation_download` — the shared resolve → pick-artifact → stream →
register core the Research audit asked for, which had been written out three separate times with three
different ideas of which DataLink row is "the science file". `uuid_from_publisher_id` was likewise
duplicated in two UI files; it keys Research records and their managed directories, so a divergence would
have split one observation into two library entries.

Still open from this phase's original list: the `fits` default-feature decision, the MCP-vs-UI export
layout split, and the citation fields the README already promises. All are Phase 8 material now.

### Phase 6 — Workflows tier (M) — **DONE except W5's store event**
W1–W4 and W6–W8 are in. `WorkflowSource::VoSpace` had been a dead enum variant; the third tier now
exists end to end — the store lists / fetches / publishes, the sidebar has a VOSpace section loaded in
the background, and local workflows have a Publish button that offers to reset progress.

`save_workflow` gained `location`, completing W3. An unknown value fails loudly rather than defaulting
to local — an agent that meant to publish would otherwise believe it had.

**The editor validates as you type (W4).** `validate` existed but nothing called it, so a typo'd
`View:` or `Tool:` only surfaced later as a dead deep-link or a hint naming a tool that was never
there. The known-tool universe comes from the live router, which is already pinned to the reference's
manifest — better than the reference's own hand-maintained list, and it cannot drift. The same
universe now guards the seven SHIPPED templates by test, so renaming a tool without updating the
templates fails the build.

Copy-prompt (W6), click-to-copy tool chips (W7) and the current-step highlight (W8) are in.

**W5 is now done too.** The store is stateless — every caller builds its own `WorkflowStore`, MCP

**Phase 6 is complete.**

### Phase 7 — Payload-shape alignment (M) — **COMPLETE**

The method that made this tractable: dump every `record Output/…View/…Wire(...)` from the reference
once, camelCase the field names, and diff the whole set against every string literal in `src/`. That
turned a vague "some payloads differ" into a list of **64 reference fields we never emitted**. 61 are
now sent.

It was not a naming exercise. The scan surfaced five defects that would have produced wrong
behaviour, not just unreadable keys:

| Defect | Consequence |
|---|---|
| `vizier_cone_search` took `radiusDeg` where the reference takes `radiusArcsec` | A 10-arcsecond cross-match swept **10 degrees** — 3600× too wide |
| `artifactIndex` indexed ALL DataLink rows, not just `#this` | CADC returns thumbnails first, so "download artifact 0" fetched a **PNG** instead of the science frame |
| `read_vospace_file` called `download_bytes` | Asking for 64 KB of a multi-GB cube **buffered the whole cube** in memory |
| `list_open_tabs` returned arrays under `notebooks`/`cubes`, ints in the reference | Same keys, **incompatible types** |
| `set_search_focus` did no range checking | `decDeg: 200` was accepted |

Two whole payloads were serialized straight from internal Rust structs, so the wire carried
snake_case field names nothing was written against: `get_current_view` (only `username` of twelve
fields matched) and `list_recent_launches`. Both are now built explicitly — the right seam anyway,
since a persisted struct and a wire contract should be free to differ.

**Three fields remain unsent, by decision rather than omission:**

- `imageIds` — a false positive. The reference pins `imageIDs` with an explicit `JsonPropertyName`,
  overriding its own camelCase policy; we already match it.
- `ExportBundleTool.Output` (`bundleDir`/`zipPath`/`remotePath`) and `VoSpaceWriteTools.Output`
  (`bytesWritten`) — an applied proposal returns a human-readable status string in our pipeline, not
  a record. The strings already carry the byte count and destination. Making these two appliers
  structurally different from every other one would be the wrong trade.

**One divergence is left standing and is now stated in the tool description instead of being
silent:** our FITS `hdu` argument is CFITSIO-native 1-based (1 = primary) while the reference and
astropy index from 0. Shifting it would mis-read every multi-extension file until we have a
header-only reader — our loader requires an image HDU, and an MEF's primary usually has none.

**Rule adopted for deliberate extras.** Divergence is allowed only when it survives one question:
*can the agent derive this itself?* `bookmarkedOnly` cannot (an empty filename is ambiguous) → kept.
`isWarning` can, from `usagePercent` → dropped, and it stays a UI concern where `is_warning()` still
serves the quota widget. `hasFits` cost a `stat()` per row — on an `/arc` mount, a network round trip
per observation — → dropped, which is exactly what the reference's "compact view, no live filesystem
probing" comment rules out.

### Cross-cutting finding: dropdowns decoded by index against a second list

Not in the audit, and found by accident — the widening of the spectral units in item 2 introduced a
live instance of it, which is how the pattern became visible at all.

GTK dropdowns carry no value, only a position. Every one of these surfaces therefore held **two**
lists: the labels the widget was built from, and an array the selection was decoded against. Nothing
tied them together, so they drift silently and the failure is a *wrong value*, never an error:

| Surface | What the drift produced |
|---|---|
| Search spectral units | The list grew 4 → 14; the combo kept the old four, so picking "Angstrom" (index 1) meant `SPECTRAL_UNITS[1]` = **cm**. A search in Ångström ran in centimetres. |
| Search rows-per-page | Labels and the decoding array sat **350 lines apart**. |
| Launch form session type | The list appeared **three times**; `selected_type` indexed its own stale copy. |
| Settings + session strip | Two more copies of that same list, and Settings *writes the value the launcher reads back*. |
| Cube export scale | Decoded by a hand-written `match` on the index; the default was a bare `1` (an index) beside a comment saying `2×` (a factor). |
| Cube export format | `selected() == 1` meant PDF, so reordering the list would have changed the file type. |

All six now build from the single list that decodes them, or read the label back off the widget's own
model. Two source-scanning guards enforce it.

**The guard is the lesson, not the fix.** Its first version stopped at the first `)`, which lands
inside `tr_en!("…")`, so it never reached the item list and passed with the bug in place. Only
re-introducing the regression and watching it stay green exposed that. A guard that cannot fail is
worse than none, because it is trusted — every source-scanning guard in this codebase should be
verified by breaking the thing it guards.

### Cross-cutting finding: a widget's limit and the tool's advertised limit disagree

The same shape as the dropdown finding, one layer down, and found by looking for it deliberately
after the first. A numeric widget CLAMPS silently; a JSON schema is a promise to the caller. Where
the two were written separately they drifted, and the widget always won:

| Surface | Widget | Advertised | Consequence |
|---|---|---|---|
| Search radius | 0–10 deg | 0–90 | A 45-degree cone became 10 |
| Search row limit | 10–30,000 | 1–30,000 | "One example row" became 10 |
| FITS zoom | canvas 1–10,000%, wheel 10–5,000% | 5–2,000% | Three answers to one question; the advertised one matched neither |
| Cube steps / spectral scale / density | clamped in the GL layer | stated in PROSE only, no `minimum`/`maximum` | A client could not validate, and an out-of-range value was clamped rather than refused — the caller believed it had set something it had not |

Each is now one constant, read by both the widget and the schema, with a test asserting they agree.
The numbers matching today was never the point: they were separate literals in separate files, which
is *why* they disagreed.

**A schema that is tighter than the enforcement is not harmless either.** It makes a validating
client refuse values the app accepts, and it tells an agent a ceiling that is not real — so the agent
plans around a limit that does not exist.

### The advertised-vs-actual finding now has a test, not just fixes

Three fixes into this pattern it was clear the next instance would be found the same way — by
someone happening to read both sides of one argument. `catalog.rs` now walks the LIVE manifest and
asks, of every declared argument, whether any argument-reading file looks it up. Getting it honest
took three passes, and the failures are the interesting part:

1. Scanning the whole source let a **schema find its own argument names** — it passed with the bug
   present. `json!` regions are stripped now.
2. The second version reported ten arguments as unread. All ten were fine: `arg()` already bridges
   camelCase and snake_case, so a reader asking for `max_bytes` receives `maxBytes`. I nearly
   "fixed" ten working tools. The scan models the bridge now — **verify before asserting**.
3. The third still passed against a deliberately broken `zoomPercent`, because descriptions and
   tests name arguments too. The literal must now sit where a LOOKUP puts it.

Verified by re-breaking `zoomPercent`. Two real finds fell out of it (item 41).

Two more invariants have since joined it, each written after a bug it would have caught:

- **What an agent can SET it must be able to READ** — otherwise it cannot restore a view it changed.
  Found the cube's four (item 42). Deliberately scoped to the three pairs where the names ARE the
  contract; `set_search_results_view` and `set_search_constraints` report their state under the
  reference's own names (`page` → `currentPage`, the facets built by iterating `FACETS`), and
  "fixing" that would mean renaming payload keys the reference already fixes.
- **A payload key an applier READS must be one a proposer WRITES** — a proposal payload is written in
  one function and read hundreds of lines away, with nothing connecting them. Found item 43, which
  led to item 44. Scoping this one took two wrong answers, both recorded in the code: scanning the
  whole file counts the tool SCHEMA's property names as writes (so the guard passed against the bug
  it was written for), and scoping to `propose_*` bodies alone missed payloads built in shared
  helpers.

### Cross-cutting finding: what a tool ADVERTISES vs what the app actually does

The third instance of one shape, and the most productive — found by deliberately looking for it after
the first two. Each is "one fact, written down twice, in files that never meet".

- **Schema enums vs the parser.** FITS stretch/colormap names were a literal in the schema and a
  `match` in the viewer. They agreed, but nothing held them together: a rename would leave the tool
  advertising a value the viewer no longer understands. Both now read one list, with a round-trip
  test — every advertised name must parse AND come back with the same spelling, or `get_fits_view`
  would report a stretch the caller never set.

- **Read name vs write name.** `get_fits_view` reports `zoomPercent`; `set_fits_view` accepted only
  `zoom`. **An agent reading the view and writing a field straight back was silently ignored** — the
  most natural thing for it to do. The cube's camera had the same split against the reference
  (`az`/`el`/`dist` vs `azimuth`/`elevation`/`distance`).

- **Controls with no tool at all.** Checking the cube's enums turned up something larger: `colormap`,
  `stretch`, `windowLo`/`windowHi`, `windowPreset`, `showCaptions` and `showSlicePlane` were neither
  declared nor parsed. Six controls in the cube's own panel, every one of them something the user can
  change — so **"100% MCP UI coverage" was not true for the cube**. They are wired now, and reported
  by `get_cube_view`: a control an agent can set but not read leaves it unable to tell what it
  changed FROM, so it cannot put the user's view back.

The lesson that generalises: comparing our tool schema against the reference's found the naming
splits, but only comparing the schema against **our own UI** found the missing controls. Parity with
the reference and coverage of our own app are different questions, and the second one needs asking
separately.
